# Successor and projection recovery

Use this guide when a stronger implementation crosses an accepted exact
version, mutable family discovery, and one or more delivery surfaces. Each
surface has a distinct recovery target.

## Name the coordinate before changing it

| Surface | Owner and useful observation | Recovery route |
| --- | --- | --- |
| Accepted exact version | Its source, manifest, tests, and immutable tag. | Preserve it; form the strengthening at a successor coordinate. |
| Successor candidate | The focused branch and current review. | Repair its source and repeat the affected behavior and derivation checks. |
| Family README or catalog | The discovery owner and accepted-current pointer. | Point to the actual accepted form; carry one re-entry move for unfinished work. |
| Generated Pages bytes | The deterministic builder and exact source coordinate. | Regenerate from the accepted source, compare complete selected bytes, then use the authorized deployment route. |
| Hosted endpoint or optional Gist | Its observed revision, response, and source/digest binding. | Inspect actual state after an ambiguous result, then complete or restore through that destination's owner. |

A successful source build establishes the generated candidate. A successful
upload establishes its delivery step. Hosted status, content, media type, and
cache behavior require a receiving observation when claimed.

## Decide whether a successor is needed

Compare the smallest fitting route:

1. Correct mutable family orientation when the accepted behavior and exact
   bytes already support the explanation.
2. Add an explicitly separate design probe when competing mechanisms still
   need an observation before selection.
3. Form a successor when code, accepted evidence, or a source-supported
   companion needs a stronger material guarantee.
4. Rest the proposal when the receiving requirement or authority remains
   unsettled; retain the exact question that reopens it.

The chosen version follows the registry's current policy and compatibility
contract. Explain any changed public input, output, platform, failure outcome,
or source relationship. Use representative prior cases alongside the new
counterexample to establish each compatibility claim.

## Partial publication exercise

Given an accepted successor and a generated site candidate, suppose the upload
returns an ambiguous transport error. Inspect the actual hosted coordinate and
bytes before repeating the operation. If the previous accepted version is
still served, the destination owner can retry the authorized publication. If
the successor is already served, verify it and complete the return. If mixed
state is observed, preserve the exact observations and use the destination's
documented reconciliation or rollback route.

This authored scenario is a decision exercise, not a completed deployment
test. A real destination may expose atomic activation, per-file writes, or an
immutable revision switch; its mechanism selects the fitting observation.

## Finish with one receiving record

The existing PR or release return can carry the predecessor, successor,
material difference, exact proof and scope, derivation comparison, destination
state, and next receiver. Preserve historical observations at the source they
actually exercised. A later accepted revision receives its own evidence when
the changed behavior requires it.
