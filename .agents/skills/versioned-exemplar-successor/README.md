# Versioned exemplar successor

Use this skill when a stronger technical guarantee belongs in a new runnable
artifact version. It preserves accepted coordinates while moving new behavior,
focused tests, exact teaching excerpts, and projection receipts through one
traceable successor route.

## Fastest start

1. Read the [skill contract](SKILL.md).
2. Bring the accepted version, manifest, source, focused tests, family pointer,
   and the counterexample that makes the strengthening material.
3. Name the new guarantee and its compatibility relation to the accepted
   version.
4. Implement and test the successor at the runnable source owner before deriving
   teaching companions.
5. Open [successor and projection recovery](references/successor-and-projection-recovery.md)
   when candidate, accepted source, family discovery, or hosted output diverge.

Example request:

> Use `$versioned-exemplar-successor` to carry this concurrency repair from the
> accepted sample into a new runnable version. Preserve the accepted coordinate,
> prove same-target races, and derive the teaching excerpt from the tested
> successor source.

## Success example

An accepted artifact proves recovery from one filesystem fault. A concurrency
counterexample requires a per-invocation candidate protocol, so a successor
version owns the new state machine and same-target race test. Its companion
selects exact source and test bytes, and publication waits for the repository's
accepted review route.

## Recovery example

A successor build passes locally while a derived excerpt points to an earlier
source digest. The team keeps the accepted version reproducible, repairs the
candidate's source mapping, regenerates the companion, and repeats the affected
checks. Hosted destinations reconcile to observed revision and digest before
another authorized projection attempt.

## Maturity and transfer boundary

This package is a version-evolution and source-authority contract. Runnable
successor code and focused tests establish their named behavior and
environments. Version selection, review, merge, immutable tagging, Gist or
Pages projection, deployment, and rollback remain with the receiving
repository's authorized owners.
