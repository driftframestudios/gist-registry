# Versioned exemplar successor

## Contract

- **What:** A source-authority route from newly observed technical pressure to one reviewable successor version and its truthful projections.
- **When:** An accepted sample meets a new material behavior requirement, a proposed teaching block differs from current source, or a companion's claim reaches beyond its focused tests.
- **Boundaries:** Immutable tags and accepted version bytes remain intact. Proposed code carries draft or experimental standing until runnable source and focused observations support it. Gist, Pages, and other publication actions retain their named human or runbook authority.
- **Result:** A successor coordinate whose runnable source owns the revised behavior, whose tests establish the bounded guarantee, and whose teaching companions resolve exactly to that source.
- **Interactions:** `architecture-convergence-vantages` owns selection while several mechanisms remain plausible; this skill begins when one operating model and material guarantee have been selected.

## Fit and attention

- **Useful when:** The strengthening changes concurrency, recovery, security, public API behavior, portability, or another material guarantee.
- **Poor fit when:** Wording alone can be corrected without changing code, evidence standing, or accepted bytes.
- **Smallest useful dose:** One successor version, the focused tests that distinguish it, and only the derived surfaces needed by a named reader.
- **Foregrounds:** Immutable history, current behavior authority, veracity standing, exact derivation, and projection timing.
- **Material result:** A receiver can run the stronger behavior and trace every teaching claim to its owner.

## Rules

### Rule: Runnable source owns the guarantee

Implementation guidance, behavioral marker comments, and recovery semantics
enter the successor source first. A companion may quote or select them after
the source and focused tests establish the claim.

### Rule: Accepted coordinates remain immutable

A tagged version stays unchanged. Material strengthenings form a fitting
successor version, and a new immutable tag forms only after review and
acceptance on `main`.

### Rule: Derivation stays exact or declares proposal standing

An exact excerpt remains byte-resolvable to its declared source and tests. A
design sketch or probe belongs to a distinct experimental artifact with
`draft_probe` or equivalent standing; it does not enter a source-supported
companion as if already implemented.

### Rule: Evidence reach changes with behavior

Name the operating model, supported environment, exact primitive, injected
failure states, and adjacent guarantees left open. Atomicity, recovery, crash
durability, concurrency, and behavior under a same-authority writer remain
distinct claims.

### Rule: Projection follows acceptance

Registry discovery, Pages output, and optional Gist materialization project an
accepted coordinate. Mutable external heads retain exact revision and digest
bindings; human review retains the publication decision.

### Rule: Historical quality decisions can reopen

New mechanism evidence may revise an earlier “retain as written” disposition.
The earlier collaboration remains accurately described at its original
evidence boundary, while the successor receives the stronger job.

### Rule: Family continuation remains lightweight

The mutable artifact-family README may describe continuation as `seeded`,
`interstitial`, or `settled`. An interstitial family names one re-entry move.
Exact-version manifests retain artifact identity and evidence standing. The
family README owns pause and re-entry context; branches and pull requests show
active work.

## Operating sequence

1. **Reconstruct authority:** Confirm branch, accepted tag, source bytes, focused tests, companion mappings, and current projections.
2. **Name the new observation:** State which guarantee or evidence boundary changes and which reader or runtime consequence makes it material.
3. **Choose standing:** Route implemented behavior to a successor version; route unsettled architecture through `architecture-convergence-vantages`, using a distinct experimental probe only when behavior evidence is needed to select the architecture.
4. **Define the successor contract:** Name the operating model, exact behavior, failure and recovery states, environment boundary, and version movement.
5. **Implement at the owner:** Revise runnable source and place `TARGET`, `CONTRAST`, and `GUARD` comments where they aid inspection of the actual mechanism.
6. **Add focused observations:** Exercise success, consequential failure, recovery failure, and any concurrency or durability claim the successor makes.
7. **Derive teaching surfaces:** Select exact source and test bytes, preserve their veracity status, and link to the complete runnable package.
8. **Validate and receive:** Run the nearest artifact checks and repository suite, review the diff against the prior version, and merge through the Issue branch.
9. **Update continuation:** Point the family README to the current form and record `interstitial` with one re-entry move or `settled` at the declared boundary.
10. **Project after acceptance:** Create the immutable tag and use the existing Pages or Gist route only when the current task grants that action.

## Scenario: A source-supported excerpt reveals a stronger architecture

Given an accepted version and exact companion demonstrate recovery for one
injected filesystem failure<br>
And review identifies concurrency, rollback-failure, or crash states outside
that evidence<br>
When the stronger implementation is selected<br>
Then the accepted version remains intact<br>
And a runnable successor owns the revised state machine and tests<br>
And its companion carries only exact selections from that successor

## Completion

The route completes when the prior coordinate remains reproducible, the
successor's behavior and evidence boundary are testable, each derived teaching
surface resolves to its owner, validation is recorded, and publication has
either reached its authorized receiver or remains explicitly held. New runtime
evidence, a changed platform, or a receiving-reader need can reopen evolution.
