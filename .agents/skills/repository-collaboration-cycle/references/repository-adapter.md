# Bind the receiving repository's implementation

Load this reference when the portable cycle enters a repository or an earlier
binding may have become stale. The binding tells a collaborator which accepted
implementation performs each selected operation and what its result means.
It is a small invocation record, not a new execution framework or permission
system.

## Select the binding route

Four publication routes were considered. Publishing every Gist implementation
dependency would faithfully carry its runbooks, scanner, builders, locks,
orientation, and tests, with a large repository-specific maintenance boundary.
A sanitized embedded implementation would give a runnable reference but create
a second owner for those commands. Deferral remains fitting when no receiver
needs the method. The selected route carries a complete portable procedure and
binds the receiving repository's existing accepted implementation. Its
consequence is a real fidelity check at each receiving boundary.

An accepted local runbook may already provide the following information. Read
and cite its current owner instead of transcribing the full procedure. Fill
only consequential gaps in one task capsule or receiving record. When no
runbook exists, the same table can bind source-owned scripts and standing
instructions directly.

## Required binding for the selected path

| Binding | What the collaborator establishes | Missing or contradictory observation |
| --- | --- | --- |
| Work owner and action grant | Material outcome, acceptance, current Issue or equivalent owner, permitted actions, held decisions, and stop event | Return the smallest decision that releases dependent work |
| Source identity | Preserved checkout, inspected revision, task-owned base, worktree state, and remote freshness | Continue labelled local observation; preserve overlapping work |
| Instructions and implementation | Accepted instruction/runbook revision and the native owners actually selected | Read the owning source at a verified coordinate; hold commands whose meaning remains unclear |
| Source and derived owners | Behavior source, tests, contracts, generated artifacts, and their version/identity relationship | Resolve the owner before changing derived bytes |
| Branch and version policy | Fitting base/prefix, review path, immutable coordinates, and successor policy where relevant | Preserve the existing coordinate while the source owner settles the relationship |
| Environment | Declared runtime, lock, required tools, existing readiness, and authorized preparation | Route the exact pending observation to a capable receiver |
| Evidence operations | Exact native command or named source observation, working context, prerequisites, effects, expected result, and coverage | Keep the corresponding claim open |
| Boundary inspection | Requested tree/index/history/artifact scope, exact identity, native detector/configuration, canary/test result, and terminal disposition | Hold handoff on findings, failed prerequisites, mismatched scope, or adapter error |
| Delivery and recovery | Receiving surface, required review/checks, last verified state, allowed external effects, and next owner | Deliver the completed reviewable portion and name the held action |

Entries apply when the selected path uses them. A source-only assessment needs
no invented branch, tool installation, aggregate runtime pass, or publication
operation. Record why an omitted lane is outside the receiving question when
its absence could otherwise imply completion.

## Read a command as an operation

Before invoking a native command, identify:

1. **Input and owner:** Which revision, index, file set, configuration, or artifact will it inspect or change? Where is its implementation?
2. **Preconditions and effects:** Does it install tools, update refs, write generated files, contact a service, or publish? Which task grant covers those effects?
3. **Observable result:** What identity and result fields distinguish success, supported absence, findings, failure, and an unobserved lane?
4. **Failure and recovery:** Which state remains accepted, where diagnostics belong, and which retry or reconciliation the native owner permits?

For a secret-material handoff, a process exit is only one observation. The
receiving implementation must establish the selected scope and its fresh
canary/test prerequisite. Distinguish observed clean, findings held, detector
or adapter error, and unobserved/resting states. Preserve the native policy on
executable trust, caches, and diagnostic handling. A safe normalized return
can name the state while raw candidates remain with their authorized owner.

## Concrete implementation differences

Gist Registry's existing source-cycle runbook owns its short-lived source
branch, exact-version artifacts, registry/schema reconciliation, and source
checks. Its Pages runbook separately owns tags, generated `docs`, and hosted
observation. Those commands remain in their repository owners.

Human–AI Systems Exemplars' accepted cycle runbook also supports detached
source observation, task-owned integration or review bases, conditional
browser preparation, domain-specific evidence, and review-held delivery.
Its scanner and publication routes retain their own implementation. A HASE
receiving assessment therefore binds those owners rather than applying Gist's
artifact version policy or Pages commands.

These named differences explain the interface; they supply no hidden package
dependency. The task provides the receiving source and accepted adapter as
inputs. The portable [procedure](source-work-cycle.md) supplies the complete
selection, execution, recovery, and return method.

## Fidelity and re-entry

Compare the selected binding with the actual native implementation before
using its result. At minimum, independently challenge one consequential
failure or interruption and verify the resulting held state, retained
coordinate, and next action. A deliberately stale scope should also remain
distinguishable from a current observation when identity drives handoff.

Binding completion means each selected operation has a current owner and a
meaningful observed result. It does not certify every command in a repository.
A changed native command, configuration, source coordinate, policy, or action
grant refreshes the affected entry and its evidence before dependent work
continues.
