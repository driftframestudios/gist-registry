# A complete source-work procedure

Load this procedure for a full task traversal. The
[adapter contract](repository-adapter.md) binds native commands and policy;
this procedure supplies the order, decisions, checkpoints, and recovery route.
Each phase records only what changes the receiving decision.

## Choose the path

| Task path | Applicable phases and complete result |
| --- | --- |
| Source-only observation | 1–2, source evidence in 5, then 6–7; one finding, decision, or held route |
| Executed observation | 1–2, necessary preparation in 3, selected execution in 4, then 5–7; one scope-bound observation |
| Implementation or repair | 1–7, with task-owned source preparation and delivery limited by the grant |
| Held decision | Preserve the last verified state, explain the material missing signal, and deliver through 6–7 |

The presence of a later phase does not authorize it. A changed task or grant
can reopen the applicable phases without repeating settled observations whose
source and premises remain current.

## Phase 1 — Recover current truth

Read the root and nearest instructions, active work owner, source, focused
tests, and relevant planning or settled rationale. Inspect current Git state
using ordinary read operations such as:

```sh
git status --short --branch
git rev-parse --show-toplevel
git rev-parse HEAD
git log -5 --oneline --decorate HEAD
```

Identify the task-owned source through its current Issue, review, or accepted
owner. A release or integration head can differ from the default branch.
Detached HEAD and absent upstream are usable observation states. Read another
coordinate through a fitting read-only source route while preserving the
original checkout. Network refresh and partial-clone object hydration have
effects of their own; use them within the available grant and label cached
facts when live observation remains unavailable.

**Checkpoint:** Name preserved checkout, inspected revision, worktree state,
current work owner, source behavior owner, remote freshness, and any material
difference between earlier records and current source.

**Recovery:** Preserve unrelated or overlapping work. An ownership ambiguity
holds the overlapping mutation while independent source reading can continue.
Return the exact missing source fact or decision that releases that action.

## Phase 2 — Select the route and bind its owners

Classify the work as active implementation, accepted work awaiting settlement,
a missing observation, or held publication. An open Issue can describe any of
these states; its title alone does not select more implementation.

Choose direct action, primary work with bounded support, or a held route. Name
the outcome, acceptance, canonical source, adapter entries, evidence, and stop
event in one task capsule. A materially different mechanism can first receive
an architecture comparison. A straightforward owner-local repair can proceed
directly.

Optional support receives one bounded question or patch scope with a starting
revision, granted actions, expected return, and stopping event. The primary
collaborator continues independent work. A deferred packet remains useful only
while its source, acceptance, and need can be refreshed before activation.

**Checkpoint:** One route owns synthesis; every selected native operation has
a source, expected result, and fitting authority. Adjacent opportunities have
an owner or a rest condition.

**Recovery:** A missing adapter entry holds its dependent command. Conflicting
instructions or scope return a compact decision surface to their owner. A
stale support premise refreshes before integration rather than becoming
evidence for the current source by association.

## Phase 3 — Prepare source and the selected evidence lane

Inspect declared runtimes, locks, installed tools, and command implementations.
Prepare only the environment the selected observation needs. A browser task,
database proof, scanner pass, and source reading have different requirements.
Record behavior-relevant environment changes and capability limits.

For authorized implementation, create or restore the native issue-specific
branch from the verified task-owned base. Read an existing branch's remote and
review relationship before resuming it. Use a separate clean worktree when
the original contains another owner's work; preserve that original state.
Follow native version and branch policy rather than inferring either from the
portable examples.

**Checkpoint:** The task has a legible source coordinate, recovery point, and
environment capable of the selected checks. Installed tools establish
readiness, while executed observations establish their own behavior claims.

**Recovery:** Missing capability leaves its named claim open. Continue source
work that remains useful, route the exact observation to a capable authorized
receiver, or return the release event. Preserve the prepared candidate while
an environment or human decision remains held.

## Phase 4 — Execute through the material owner

Inspect or change the source that creates the requested behavior. Read its
focused tests as part of the same mechanism. Apply native immutable-version
policy, update a generator when it owns derived bytes, and keep local
observations outside accepted artifact membership unless the source contract
requires them.

For each support return, verify source revision, assumptions, diff, observed
result, and coverage against current work. Integrate only the part whose
premises remain valid. A new source owner, operational effect, or material
outcome receives a bounded scope decision instead of silently enlarging the
current task.

**Checkpoint:** The result belongs to the canonical owner, satisfies the
selected scope, and preserves unrelated work and accepted coordinates.

**Recovery:** Return a failing mechanism to its source owner with the last
verified state. If an operation may already have taken effect, use its native
receipt or reconciliation route before retrying. A command failure alone
does not establish that every effect was rolled back.

## Phase 5 — Establish fitting evidence

Select an independent expected result and a plausible fault that the check
must distinguish. Run the nearest focused checks during iteration. Run the
aggregate, generated-source, exact-index, or other handoff observations that
native acceptance requires at the candidate's actual coordinate.

For each observation, retain this relationship:

```text
Source/index/tree/artifact identity + command or named source reading
  → normalized observed result
  → the specific state it establishes
  → adjacent claim and its remaining evidence owner
```

A source reading can establish ownership or a reachable branch. A runtime
test establishes the behavior it actually observes. A deterministic build
establishes membership and byte agreement under its declared inputs. Hosted
delivery, audience comprehension, platform behavior, and human acceptance
keep their own evidence boundaries.

Inspect the exact handoff scope through the selected native boundary owner.
Require its declared canary/test prerequisite and distinguish clean, findings,
adapter error, and unobserved states. Keep diagnostic material with its
authorized receiver; public returns carry normalized conditions.

**Checkpoint:** Evidence answers the active criteria at the proposed bytes.
Remaining criteria name the missing observation or decision explicitly.

**Recovery:** A failed check returns to its source owner. A failed canary,
mismatched scope, or detector error holds the dependent handoff. A later source
change invalidates only the observations whose inputs or premises changed;
native required aggregate gates still run at their declared delivery point.

## Phase 6 — Deliver at the granted boundary

Inspect the complete diff and retained state. Where authorized, prepare the
exact intended index, run the native staged boundary, commit, push, and open
the fitting review surface. Where the task asks only for observation, one
decision-ready task response can complete delivery.

Compare the result with the work owner's original acceptance. Preserve any
remaining criterion and identify its next receiver. A refinement of ambiguous
language can be recorded transparently; it cannot silently redefine an unmet
outcome as completed.

Use one durable receiving surface:

```text
Result: material change, observation, or held condition
Source: inspected/proposed/accepted coordinate and work owner
Changed surfaces: concise repository-relative paths or decision
Evidence: exact command or source observation → normalized result
Establishes: the affirmative observed state
Coverage: adjacent claim and its receiver
Environment: relevant preparation or capability difference
Retained state: last accepted or recoverable coordinate
Next receiver: review, acceptance, observation, or held decision
Re-entry: one exact action and the event that permits it
```

**Checkpoint:** The receiver can assess the result, its evidence, and the next
action without following a chain of duplicate receipts.

**Recovery:** Changed review head, base, checks, or findings return to the
affected source phase. A review-ready result completes a review-granted task.
Further merge, tag, publication, or deployment follows the existing receiver
and action grant; accepted external state remains at its verified coordinate.

## Phase 7 — Confirm continuation and release

Report final source, worktree, work-owner standing, and exact continuation.
If integration was granted and completed, verify the accepted coordinate.
If a decision remains held, name its responsible receiver and observable
release event. Retain a useful recoverable candidate rather than generating
additional work to fill the interval.

The cycle releases when the promised result or correctly held route reaches
its receiver. A changed source, adapter, acceptance, capability, or grant
reopens the matching phase. A future collaborator can begin from that precise
point while earlier observations retain their actual historical scope.

## Scenarios that change the route

- **Observed work is already accepted.** Given an open Issue and an older plan, when current source and review show implementation is accepted, then the cycle selects the remaining settlement or observation receiver and preserves the accepted bytes.
- **The checkout belongs to another task.** Given overlapping local edits or a newer checkout, when the requested source has a different coordinate, then observation reads that source without resetting the checkout; authorized implementation receives a separate task-owned context.
- **Inspection cannot establish the requested boundary.** Given a prepared candidate, when the native canary fails or the returned scope differs, then handoff remains held, diagnostics stay private, and the result names the exact repair/re-observation owner.
- **Support becomes stale.** Given a bounded review return, when its premise predates a material source change, then synthesis refreshes the affected observation before adoption and keeps unaffected primary work moving.
- **Source is ready and publication is held.** Given passing source checks and a review-only grant, when the receiving PR is ready, then the source cycle completes and names the separate publication decision and re-entry event.
