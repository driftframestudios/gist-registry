# AI collaboration runbooks

Runbooks give AI collaborators a re-entrant route through a known multi-phase
procedure. GitHub Issues retain outcomes and acceptance; the current task grant
retains mutation, publication, deployment, and external-action authority.

| Runbook | Use it when | Standing |
| --- | --- | --- |
| [Gist Registry cold-session entry](gist-registry-cold-session-entry.v0.1.md) | A cold or resumed collaborator should reconstruct current truth, classify the work front, select proportionate context, and form one task capsule | Exercised through Issue #31 as a fresh-context settlement traversal; accepted through Issue #41 and pull request #42 |
| [Gist Registry source collaboration cycle](gist-registry-source-collaboration-cycle.v0.1.md) | One active Issue should move from current truth through canonical source, proportionate evidence, and a reviewable pull request | Exercised through Issue #18 / PR #22 and an independent fresh-context source cycle |
| [Gist Registry Pages publication](gist-registry-pages-publication.v0.1.md) | An accepted `main` revision is ready for deterministic `docs` projection, GitHub Pages reception, and ordinary-domain byte observation | Exercised through two real publication cycles and an independent cold-start traversal |
| [Gist Registry receiving-repository use](gist-registry-receiving-repository-use.v0.1.md) | Another repository should select, verify, adapt, observe, and report on one exact Registry coordinate | Exercised on two distinct candidate package mechanisms, including one independent cold-entry review; the [receipt](receipts/gist-registry-receiving-repository-use.v0.1.json) keeps source acceptance with its review owner |

`working`, `exercised`, `stable`, and `retired` describe observed maturity.
They confer neither permission nor priority. A runbook releases when its
receiving state and handback are complete; a changed owner or route reopens the
matching phase through its active Issue.
