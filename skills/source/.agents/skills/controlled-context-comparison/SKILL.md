# Controlled context comparison

## Contract

**What:** Construct paired observations that isolate a declared input change while preserving source evidence, admissible dependencies, output classes, and accountable interpretation.

**When:** A team asks whether an administrative, contextual, policy, presentation, or model-input difference changes a downstream result.

**Boundaries:** A controlled software experiment establishes behavior within its declared construction. Wider causal, population, fairness, and operational claims retain fitting designs and accountable reviewers.

**Result:** A versioned pair specification, independent invariants and expected effects, complete outcome accounting, and a bounded interpretation.

## Fit and attention

Useful when input generation can leak target information, one changed field affects several downstream stages, or stochastic output complicates interpretation. A direct source comparison suffices for a simple deterministic equality question. The smallest useful dose is one pair, one material contrast, and one receiving decision.

## Rules

- State the input concept precisely. A raw label, normalized class, eligibility state, policy decision, and output action are different variables.
- Bind invariant source material by identity/digest and explicitly allow only the declared intervention and required dependent transformations.
- Preserve construction order and provenance. A feature derived from the target remains visible as target-dependent information.
- Compare task meaning before comparing bytes. If a coding change adds scientific information, select a separate information-content study or an equivalent-information design.
- Separate scientific/source-evidence conclusions, administrative routing, workflow burden, explanations, and authorized effects.
- Hold model/prompt/retrieval/tool versions constant where possible; record actual routing and residual stochasticity. A fixed seed alone supplies a limited repeatability claim.
- Include unchanged-input repeats and a designed effect that the observer must detect. Independent expected results protect against a comparator that always reports agreement.
- Count incomplete, failed, abstained, and rejected cases with their own outcomes and denominators.
- Match uncertainty to the unit of inference. Repeated runs and records from one subject/episode remain clustered.
- A finding routes to its mechanism owner and named reviewer. A materially different result can be valid rather than an automatic implementation defect.

## Operating sequence

1. Bind the decision, task, scenario, source, jurisdiction/effective dates where relevant, and reviewer role.
2. Classify the changed concept, fixed facts, allowed dependent changes, and output families.
3. Specify the pair, independent invariants, positive control, unchanged-input control, and stopping rule.
4. Execute only within the task's granted environment/data/model authority.
5. Classify results, failures, uncertainty, and affected mechanisms.
6. Return one bounded disposition and the next evidence or authority event.

## Boundary scenario

Given a category code and a leaf code imply different information, when the question concerns administrative status alone, then the comparison supplies equal underlying evidence to both arms or explicitly becomes an information-content experiment. The interpretation names the design actually exercised.

## Completion and re-entry

Complete when the comparison identifies what changed, what remained fixed, which effect is supported, its evidence boundary, and the next receiver. Reopen when source, generation order, task, policy, model, or receiving use changes.
