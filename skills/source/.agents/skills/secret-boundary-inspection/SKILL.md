# Secret-boundary inspection

## Contract

- **What:** A portable inspection procedure that binds detector liveness, a named material scope, protected feedback, and the receiving handoff's next move.
- **When:** Source, a proposed commit, locally available history, or an artifact is preparing to cross a repository or publication boundary.
- **Boundaries:** The receiving repository owns its scanner, installation evidence, configuration, supported scopes, and tests. The current task grants execution; credential validation, disclosure, access rotation, history mutation, and publication retain their accountable owners. A clean scan establishes its detector observation within the named scope.
- **Result:** A verified receiver mapping, a fresh canary result, each requested scope's disposition, and one safe receipt or private response route.

## Fit and attention

- **Useful when:** A commit, generated output, ignored local file, or receiving assembly needs a credential-shaped-material observation.
- **Direct route when:** An unchanged accepted repository command already supplies the required observation and safe receipt.
- **Poor fit when:** The question concerns live access administration, exhaustive object forensics, publication permission, embedded metadata, or signed-out delivery. Those jobs keep separate evidence.
- **Smallest useful dose:** One accepted receiver implementation, one fresh canary, one precisely named scope, and one bounded return.
- **May under-attend:** Unfetched refs, forks, caches, historical binary content omitted from patches, hosted prose, provider validity, and audience suitability require their own observations.

## Inputs, defaults and output

Bind the receiving repository and accepted source state, task authority, requested
scope, scanner/configuration owner, and the person or Issue receiving the result.
Read the local implementation record before choosing commands. The
[adapter contract](references/receiver-adapter-contract.md) identifies the
required responsibilities without prescribing an engine or a new framework.
An absent mapping returns a held observation and its missing owner; the portable
skill supplies the questions needed to complete it.

Use local detection with provider validation resting unless the task explicitly
grants a different operation. Keep raw reports and diagnostic objects inside the
receiving implementation's private boundary. The public return contains only
approved identities, scope, canary outcome, completion or failure category, and
coverage limits. A resting index, an unobserved scope, and an observed clean
scope remain different states.

## Rules

### Rule: The receiving implementation owns behavior

Locate the wrapper, installation/version evidence, reviewed configuration,
focused tests, and local orientation. Establish their current source identity.
Use the receiver's existing commands and failure handling; a portable contract
routes and challenges that behavior. A change in engine, dependencies, input
scope, suppression policy, or output projection reopens adapter review.

### Rule: A fresh canary proves the selected path

Generate a new non-issued provider-shaped value for each operational canary.
Require the selected rule, finding exit, report parser, redaction, and protected
feedback to work together before interpreting scope results. Prefer transient
standard input. Synthetic index/history tests may create bounded temporary Git
fixtures; their owner removes those fixtures after observation. A missing
canary or mismatched result holds the handoff at detector verification.

### Rule: Scope is part of the result

Separate current tree, exact proposed index, diff-visible local history, and
named artifact. State ignored/generated inclusions, cache exclusions, supported
entry types, and quiescence assumptions. An exact-index claim requires the
indexed bytes, including unchanged entries; a changed-lines scan supplies a
narrower observation. The receiver handles filters, alternate indexes, partial
acquisition, and temporary cleanup through its own tested implementation.

### Rule: History follows ref acquisition

Establish clone completeness and locally available refs before scanning history.
A non-shallow clone and an all-local-ref scan still leave unfetched remotes,
forks, dangling objects, caches, hosted prose, and bytes absent from textual
patches outside the result. Name those limits and route any wider investigation
to a separately authorized evidence owner.

### Rule: Finding, error, and clean retain separate meanings

A clean exit plus the expected empty report can support clean standing after the
canary passes. A designated finding exit plus admitted findings holds the
affected handoff for private triage. Unexpected exit, signal, malformed report,
redaction failure, contradictory exit/report, missing scope, or unknown state
holds the observation as incomplete. A detector failure supplies a recovery
question, rather than a zero-finding result.

### Rule: Protected feedback survives the failure path

Treat raw stdout, stderr, filenames, commit messages, fingerprints, report
attributes, exception causes, and candidate values as potentially sensitive.
The receiver projects only its bounded approved fields. Selectively masked
match fields alone leave other report fields unreviewed. Test the returned
object and rendered error as well as ordinary success. An unexpected failure
receives a fixed safe category; authorized diagnostics retain the cause.

### Rule: Exceptions have one reviewed owner

Use the receiver's declared configuration surface for fixture or indirection
exceptions. A new exception names its precise path, rule/value shape, rationale,
and distinguishing test. Ignore files, baselines, or inline allowances enter
only through an explicitly adopted local policy. Preserve useful findings while
the owner decides their status.

### Rule: Recovery preserves the affected boundary

Keep a candidate inside private triage and pause the affected handoff. When live
access is plausible, return containment and rotation to the credential owner
before coordinated repository cleanup. A scanner failure returns to the
implementation owner; source and accepted artifacts stay intact. Resume after
the repaired canary and affected scopes pass. A receiving repository observes
its own assembled material using its accepted implementation.

## Operating sequence

1. **Bind:** Name receiver, accepted source, authorized action, requested scopes, return owner, and stop event.
2. **Map:** Resolve the local adapter responsibilities and current commands; separate unsupported scopes.
3. **Verify:** Check installation/configuration identity and fitting implementation tests after relevant changes.
4. **Prove:** Run a fresh canary and hold interpretation when any decisive check fails.
5. **Observe:** Execute the named scopes with protected output and scope-specific identity.
6. **Return:** Supply one safe result to the existing work record, or the held state and its private recovery owner.

## Decisive scenarios

### Scenario: A clean tree accompanies a different proposed index

- Given the worktree contains a runtime indirection while the index retains an earlier candidate-shaped value
- When the proposed commit receives inspection
- Then the exact-index owner observes indexed bytes and the handoff remains held
- And the source owner repairs the proposed index before its canary and scope are repeated

### Scenario: The detector fails after a successful canary

- Given the current canary passed and an artifact scan exits unexpectedly
- When the adapter prepares the receiving return
- Then it reports an incomplete observation with fixed feedback and preserves the artifact
- And the implementation owner restores the scanner before artifact acceptance resumes

## Completion and re-entry

Complete when the accepted detector path has a fresh canary, each requested
scope is observed or explicitly held, and the receiving owner can take its next
authorized move. Release the route when an existing command already carries
that result. A changed scanner, configuration, scope, source assembly, or actual
finding reopens only the affected responsibility. Independent review and
same-lineage reuse establish their named observations; cold-start transfer
needs an independent receiver's actual use.
